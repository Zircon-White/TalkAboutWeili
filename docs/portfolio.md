## 一个 AI 角色交互系统的设计与实现

## 0. 一句话

**用一套「标签协议 + 正则中间件 + 前端运行时」，把纯文本对话扩展成可交互的场景（开门、调酒、街机），并让 AI 在对话中调用生图、语音合成、音乐检索与自建手机应用。**

四个数字（面试必背）：

| 指标 | 数值 |
|---|---|
| 单角色单存档对话 | **1100 轮** |
| 全部存档累计 | **约 10 万回合** |
| 单次生成上下文 | **8831 token**（实测） |
| 系统模块 | **7 个**（主对话 / 记忆 / 绘画 / 声音 / 互动 / 音乐 / 手机互动） |

---

## 1. 问题：SillyTavern 只是一个聊天框

SillyTavern（下称 ST）本质上是一套**灵活的提示词系统**：预设结构决定本次发送什么提示词，模型返回文字，仅此而已。

它能写得很动人，但有三条硬边界：

| 边界 | 具体表现 | 后果 |
|---|---|---|
| **只有文字** | 角色说"我给你调了杯酒"，屏幕上还是那行字 | 沉浸感断裂 |
| **没有状态** | 时间、天气、随身物品、手机界面都不存在 | 角色活在真空里 |
| **没有记忆管理** | 上下文一长就遗忘、人设漂移、token 爆炸 | 长线剧情跑不动 |

我要做的不是"更好的提示词"，而是**给这套提示词系统加一层运行时**：让 AI 的输出不只是给人读的文本，而是**给机器执行的指令**。

### 2.2 一句话概括

> **标签即 API，正则即中间件，前端即运行时。**

- AI 不需要会写代码，只要在正确的位置吐出正确格式的标签；
- 正则层是解析器，把"自然语言里的指令"翻译成"系统调用"；
- 前端是运行时，把系统调用的结果渲染成用户能看见、能点的东西。

## 3. 七个模块

主对话 · 记忆 · 绘画 · 声音 · 互动 · 音乐 · 手机互动。

### 3.1 提示词层：预设结构决定"这一次发什么"

- 用**预设（preset）**固定消息组装顺序：系统指令 → 角色卡 → 世界书 → 记忆简报 → 最近正文 → 用户输入。
- 角色卡负责"是谁"，世界书负责"世界怎么运转"，两者分离，改人设不会污染设定。
- 提示词内部按**功能分块**（叙事要求 / 角色塑造 / 行文规则 / 文风 / 禁词 / 格式协议），每块可单独替换——这是后面能做 A/B 对照的前提。

### 3.2 解析层：五类标签，五种能力

| 标签类型 | AI 输出 | 解析后发生什么 | 依赖 |
|---|---|---|---|
| **时间** | `<bbs_start>2024/10/3 12:08</bbs_start>` | 前端显示数字时钟，并随剧情推进 | 纯前端 |
| **音乐** | `<music_recommend><title>…` | 解析为播放器卡片，前台载入 | 联网检索 + 播放器 |
| **图片** | `<img>雨夜的霓虹街道</img>` | 调用生图 API，返回图片卡片 | **Seedream API** |
| **语音** | `[莫蒂默, 温和无奈] "…"` | GPT-SoVITS 用该角色音色合成，替换为语音条，点击即播 / 自动朗读 | 本地 TTS + 自训音色 |
| **交互** | `<interact>拉开车门</interact>` | 副 AI-2 生成 HTML/CSS/JS，渲染成可点击组件 | 副 AI-2 + 前端注入 |

**语音那一项值得单独说**：我在本机内置了 GPT-SoVITS，自己搜集语料训练出对应角色的音色，所以同一个角色在"说话"和"被叙述"时是两种质感——这是纯文本方案做不到的。**17 秒音频约 10 秒生成**，接近实时。

### 3.3 编排层：为什么是"三个 AI"

单一模型做不了这件事，因为它要同时负责"写得好看"和"判断哪里该交互"，两个目标会互相打架。

拆成三段流水线：

1. **主 AI**：只负责写正文，追求文字质量与角色一致性。
2. **副 AI-1（互动判定）**：读取**最近两回合**的上下文，判断本回合哪些描写应被转成可交互动作（开门、调酒、街机……），包进 `<interact>` 标签并写明交互内容。
3. **副 AI-2（代码生成）**：只读标签内的内容，生成对应的 HTML/CSS/JS，交给前端渲染。

**拆分的收益**：主 AI 的注意力不被"写代码"占用，文字质量不下降；判定与生成上下文干净，出错可定位、可单独重跑。

### 3.4 渲染层：在不破坏 ST 的前提下，做出它不让做的事

ST 对前端脚本有保护，直接注入 JS 会被拦住。我的做法是**不修改本体、不破坏它的脚本保护**，在前端挂载交互组件。

两个关键设计：

- **悬念折叠**：交互触发前，把标签之后的正文先折叠，用户完成动作（开门、按键）后才展开。这是"交互设计"而非"技术实现"——它解决的是"如果提前把结果给用户看，交互就没有意义了"。
- **手机 OS 桌面**：对话之外挂了一套手机界面（便签 / 动态 / 息屏 / 阅读器 / 小游戏）。最特别的是「**AI 现场创作**」：用一句中文描述想要的应用，AI 现场写出插件源码并直接安装到桌面——我测的用例是"一个 UNO 小游戏，玩家与三名 AI 一起游玩"，生成后能直接开局。接口可在 DeepSeek / OpenAI / 通义 / 本地 Ollama 之间切换。

> 这是整个系统里最像"平台"的部分：它不只是"AI 能调用工具"，而是**AI 能扩展界面本身**。

### 3.5 记忆层：把 8831 token 花在刀刃上

长线剧情的敌人不是模型不够强，是**上下文被无差别地塞满**。

做法：

1. **向量召回**：用向量模型把历史切片，按当前语境召回相关片段，而不是全量塞入。
2. **递进摘要**：每回合由副 AI 先概括本回合，再按固定回合数做二次、三次摘要。
3. **摘要二分**：
   - **「故事」**——过去发生了什么（事件线）
   - **「信息」**——这个角色是个怎样的人（人设线）

结果：单次生成稳定在 **8831 token**。作为一个对照——不做摘要时，每回合仅正文就让上下文**至少增加 1500 token**；1000 回合累计约 **750 万 token**，压缩后的历史摘要约 **5000 token**。剧情连贯性和人设稳定性都没有掉。

二分的直觉是：**事件会过期，人设不会**。混在一起摘要，模型会把"她昨天喝了酒"和"她讨厌被命令"当成同等权重的事实——前者很快没用，后者永远有用。

### 3.6 提示词不是文案，是一门 DSL ← 核心方法论

> 这一节是全篇最想被读到的地方。它说明"提示词工程"不是玄学，而是**有约束、可解析、可复现的工程**。

我把这套提示词按三个性质来设计：**可执行、可解析、可复现**。

#### A. 可执行：把抽象要求改写成能判定对错的规则

| 手法 | 具体做法（来自我的预设） | 为什么有效 |
|---|---|---|
| **人格化指令** | 规则不写成"你必须"，而写成角色"小此"的自我要求："小此不客串""咱知道啦～" | 约束变成角色行为，模型不会把它当成外部命令而僵硬执行，同时规则依然明确 |
| **负面清单优先** | 直接列禁词：`共犯` `薄茧` `嘴角弧度` `手指泛白` `一丝` `四肢百骸` `不是…而是…` | "写得自然一点"无法执行，"禁用这 15 个词"可以执行。**用具体反例代替抽象形容**，是提升文风最快的一招 |
| **可判定性** | "对白前后不写声音""不用括号解释""转折句全砍""比喻只用暗喻不用明喻" | 每一条都能当场判对错，模型不会理解偏差，我也能验收 |

#### B. 可解析：让输出变成下游系统能吃的结构

- **标签协议**：`[角色, 情绪] "台词"` —— 语音模块靠它切分"谁在说、什么情绪"。
- **双时间锚点**：`<bbs_start>` / `<bbs_end>` —— 记忆系统靠它切片、建时间线。"能定位到某一刻"是硬要求，禁止"稍后""不久"。
- **结构化附属块**：`<music_recommend>`（歌名/歌手/理由/内心独白）、`<options>`（四个选项分角色）——这些不是给人看的装饰，是**给插件读的接口**。

> 换句话说：**提示词层的输出格式，就是这套系统的 API 契约。** 改一个字，下游就崩——所以它必须像接口一样被设计，而不是像文章一样被写。

#### C. 可复现：把"想"也变成流程

- **强制规划**：正文前必须输出 `<konatan_planning~>`，逐项回答：当前时间/位置/关系 → 剧情方向 → 角色**知情范围**（要求 200 字以上）→ 文风限制 → 字数控制 → 如何衔接上一段。等于把"写作前的检查清单"外置成模板。
- **情绪激活**：planning 里有一句"回忆对垃圾剧情的愤怒，恶狠狠地鄙视撕咬无聊又公式的剧情"。这不是中二，是在对抗模型的**平均值倾向**——不推它一把，它就会写出最安全、最平庸的那版。
- **分层可替换**：叙事/塑造/行文/文风/禁词/格式各自成块，可以只换一块做 A/B。**"提示词格式优化能提升活人感"这个判断就是从这儿来的**——同一段剧情、不同结构，读起来差别明显。
  > 注意诚实边界：这是长期调参的体感对比，没有做严格 A/B 统计。面试时说到这一层就停，别夸大成"实验结论"。

#### 这套 DSL 的代价（也要说）

- 禁词表会越写越长，规则之间会互相打架（"鼓励语出惊人" vs "剧情推进尽可能慢"），必须有优先级。
- 规则越硬，模型越容易"表演遵守"——表面不写禁词，实际换一种套话。所以每隔一段时间要重读产出，删掉失效规则。
- 强 planning 会吃掉 token，必须和 8831 的预算一起算。

### 3.7 成本架构：贵模型只做最贵的事

| 环节 | 用什么 | 为什么 |
|---|---|---|
| 主写作 | **Gemini 4-Argon**（旗舰） | 文笔是唯一值得花旗舰模型的地方 |
| 剧情总结 / 归纳 | **DeepSeek Flash** | 压缩是机械劳动，便宜模型足够 |
| 向量记忆与召回 | **硅基流动免费向量小模型** | 召回只要"够准"，不需要贵 |
| 生图 | 生图 API | 不自建推理，省运维 |
| 语音 | 本地 GPT-SoVITS（自训音色） | 音色是独占资产，必须本地 |

**这套分工的结果**：单次生成 8831 token，长线跑下来成本可控。核心判断是——**把"智能"集中在写作一步，其余全部下沉到便宜模型、免费 API 和本地**。

## 5. 我踩过的三个坑

> 面试官最爱问"你遇到最大的困难是什么"。别答"很难"，答这三个。

**坑 1：ST 不让跑 JS。**
限制是保护，不是 bug。硬改会破坏升级路径。最后选择"不改本体、只在前端挂载"，代价是自己处理组件生命周期与样式隔离。

**坑 2：交互提前剧透。**
第一版做完发现，用户看到"门开了"再点"开门"，交互就成了摆设。改成"折叠后续正文，动作完成后展开"才成立。**这是我第一次意识到：交互设计的时间顺序，比交互本身更重要。**

**坑 3：上下文爆炸。**
直接把历史全塞进去，几轮之后就又慢又贵还失忆。改成向量召回 + 递进摘要 + 故事/信息二分，才把 8831 token 稳住。

## 6. 如果把它做成产品

> 这一节是给 AI 产品岗看的。前面证明"我能做出来"，这一节证明"我知道它值多少钱"。

**用户是谁**：不是在找"聊天机器人"的人，是在找"能一起演下去"的人——语C、跑团、乙女、互动小说玩家。他们要的不是回答，是**可预期的世界**。

**核心洞察**：这类用户真正付费的点不是"角色更聪明"，是"**世界不会穿帮**"。时钟会走、音乐会响、门真的能开——这些细节才是沉浸感的来源。

**MVP 该砍到什么**：只留"交互标签 + 悬念折叠"两件事，其余（生图、语音、手机 OS）都是加分项，不是必需项。

**北极星指标**：单次会话的**交互触发次数 / 千轮**（而不是对话轮次）——它衡量的是"世界被使用"的程度。

**风险**：① 标签协议不稳定，模型一换就崩，需要容错与降级；② 多 AI 编排成本随轮次上升；③ 版权与内容合规；④ **AI 生成的代码在本地执行，安全边界必须先划清**。

## 7. 局限与反思

- 这是**个人系统**，没有真实用户数据，所有"效果"都是我自己的体感 + 少量朋友试用，样本极小。
- 标签协议是我自己定的，没有标准化，换模型/换前端就要重适配。
- 三 AI 编排成本高于单模型，我只在"长线剧情"这一场景证明了它值。
- 提示词规则越多，越容易"表演遵守"，需要定期重读产出、淘汰失效规则。
- 下一步：把标签协议抽象成 schema，让它能迁移到 ST 之外的前端。

> - 设计三段式编排（主 AI 生成 → 副 AI 判定互动点 → 副 AI 生成交互代码）与「向量召回 + 故事/信息二分摘要」，单次生成稳定在 8831 token。

## 附 B：60 秒口述版（面试背这个）

> 我做的不是"玩酒馆"，是给酒馆加了一层运行时。
> ST 本质上是个提示词系统，模型只吐文字。我让它吐**标签**——时间、音乐、图片、语音、交互，五类。然后用正则当中间件解析标签，前端当运行时渲染出来。所以角色说"门开了"，屏幕上真的会出现一扇能点的门。
> 这里有个坑：让一个模型既写正文又写代码，文字质量会掉。所以拆成三个 AI：主 AI 只写，副 AI 判断哪段该变交互，第二个副 AI 只负责生成 HTML。
> 长线剧情会 token 爆炸，我做了向量召回加递进摘要，还把摘要拆成"故事"和"信息"两路——事件会过期，人设不会。现在稳定在 8831 token。
> 提示词我也当成接口在设计：输出格式是给插件读的，禁词表是给文风兜底的，正文前还有一段强制 planning。
> 最有意思的是手机桌面——AI 可以在剧情里给用户"装"一个新应用，相当于界面本身可扩展。
