# 标签协议规范 v0.1

> 本文档定义 **AI 输出 → 前端组件** 之间的接口契约。
> 它不是"提示词技巧"，而是一份**可解析、可校验、可降级**的格式规范——
> 改一个字段名，下游解析器就会静默失效。

> ⚠️ 状态：草稿。字段名与正则表达式以 `regex/` 下的导出文件为准，此处为语义描述。

---

## 0. 为什么需要协议

SillyTavern 里的模型只会返回一段文本。要让它驱动界面，只有两条路：

| 方案 | 问题 |
|---|---|
| 让模型直接写 HTML/JS | 模型写代码不稳定、不可控、有注入风险；文字质量也会被拉低 |
| **让模型写结构化标签，由解析器转成组件** | 模型只需吐格式，系统的行为完全可预测 |

本协议选后者。核心判断：

> **提示词层的输出格式，就是整套系统的 API 契约。**

因此它必须满足三个性质：

- **可执行**——每条规则都能当场判对错（"禁用这 15 个词"而不是"写得自然一点"）
- **可解析**——输出能被正则稳定切分，不依赖模型"配合"
- **可复现**——同样的输入结构，产出一致；换模型只影响文风，不影响系统行为

## 1. 通用语法

| 项 | 约定 |
|---|---|
| 包裹符 | 优先使用类 XML 标签 `<name>…</name>`；语音用方括号 `[角色, 情绪]` |
| 命名 | 小写 + 下划线，统一 `snake_case` |
| 嵌套 | 允许一层嵌套，禁止三层以上 |
| 位置 | 标签必须出现在**正文之后**，不得插入句子中间 |
| 编码 | UTF-8，不转义中文 |
| 未知标签 | 解析器必须**原样保留**，不得删除用户可见文本 |

解析器对**格式不完整**的标签（只开不闭、闭合错位）必须走降级路径，而不是抛错——
模型偶尔漏闭合是常态。

## 2. 时间

```text
<bbs_start>2024/10/3 12:08</bbs_start>
…正文…
<bbs_end>2024/10/3 12:08</bbs_end>
```

| 项 | 说明 |
|---|---|
| 语义 | 声明本段剧情发生的**起止时刻**（世界内时间，不是真实时间） |
| 消费者 | 时钟组件、记忆层（切片与时间线） |
| 硬要求 | 必须是绝对时刻；**禁止**"稍后""不久""过了一会儿" |
| 降级 | 缺失时沿用上一条消息的时间；首条缺失则隐藏时钟 |
| 设计理由 | "能定位到某一刻"是记忆系统切片的前提，模糊时间会让时间线断裂 |

> 双锚点（start/end）而不是单锚点，是为了支持"一段剧情跨越多个时刻"（如整晚的对话）。

## 3. 音乐

```text
<music_recommend>
  <title>发如雪</title>
  <artist>周杰伦</artist>
  <reason>明明是找个人一起骂这桩盲婚哑嫁的，怎么看着她眼红的样子，连口气都有点生不起来了。</reason>
  <thought>这姑娘说话真有意思…</thought>
</music_recommend>
```

| 字段 | 必填 | 语义 |
|---|---|---|
| `title` | ✅ | 曲名 |
| `artist` | ✅ | 演唱者，用于检索 |
| `reason` | ✅ | **角色为什么在此刻听这首歌**——这是给读者看的，也是判定角色状态是否自洽的依据 |
| `thought` | ○ | 角色没说出口的内心话 |

| 项 | 说明 |
|---|---|
| 消费者 | 播放器卡片 + 联网检索 |
| 降级 | 检索失败 → 只渲染卡片文字，不报错 |
| 常见失败 | 模型给出不存在的歌名；必须允许"查无此曲"并保留卡片 |

> `reason` 字段是这个标签最有价值的部分：它把"BGM"变成了**叙事的一部分**。

---

## 4. 图片

```text
<img>雨夜的霓虹街道</img>
```

| 项 | 说明 |
|---|---|
| 语义 | 请求生成一张图，内容为标签内的中文描述 |
| 消费者 | 生图 API → 图片卡片 |
| 硬要求 | 描述必须是**可视觉化的场景**，不得是抽象情绪或剧情评论 |
| 降级 | API 超时/失败 → 显示占位卡 + 原始描述文本，剧情不中断 |
| 限流 | 单回合最多 1 张；超出的忽略并记日志 |

> 生图是异步的，**不能阻塞正文渲染**。正文先出，图片后到，卡片位置预留。

---

## 5. 语音

```text
[莫蒂默, 温和无奈] "我这不是在夸你。"
```

| 项 | 说明 |
|---|---|
| 语义 | 声明一句话的**说话人**与**情绪**，用于选择音色与语气 |
| 消费者 | GPT-SoVITS（自训音色）→ 音频条 |
| 硬要求 | 说话人必须是已注册音色的角色；情绪为开放词表 |
| 降级 | 未注册角色 → 纯文本；合成失败 → 纯文本 + 重试按钮 |
| 性能 | 17 秒音频约 10 秒生成，因此**必须异步**，不能等 |

> 同一角色在"说话"（语音条）和"被叙述"（正文）时是两种质感——
> 这是纯文本方案做不到的，也是自训音色的意义所在。

## 6. 交互

```text
<interact>拉开车门</interact>
```

| 项 | 说明 |
|---|---|
| 语义 | 把一句描写变成**可点击的交互动作** |
| 消费者 | 副 AI-2 → 生成 HTML/CSS/JS → 前端挂载 |
| 触发者 | 副 AI-1（读取最近两回合上下文判定），不是主 AI |
| 硬要求 | 标签内容必须是**动作**，不是结果（"开门"而非"门开了"） |
| 降级 | 代码生成失败 → 退化为纯文本按钮，点击直接展开 |
| 安全 | 生成的代码在**隔离容器**内执行，禁止访问父窗口与网络 |

### 6.1 悬念折叠（协议之上的行为规则）

标签本身只声明"这里有个交互"。渲染层还必须遵守：

1. 交互组件出现时，**标签之后的正文一律折叠**
2. 用户完成动作后，才展开后续正文
3. 展开是**单向**的，不可回退

> 如果提前把结果给用户看，交互就没有意义了。
> 这是交互设计，不是技术实现——但它是协议能成立的前提。

## 7. 解析顺序与优先级

```text
正文 → ① 时间锚点 → ② 语音标记 → ③ 音乐块 → ④ 图片块 → ⑤ 交互块 → ⑥ 移除 planning
```

| 顺序 | 理由 |
|---|---|
| 先时间 | 后续所有内容都需要归属到同一时间轴 |
| 再语音 | 语音标记会切分正文，必须在其他块提取前完成 |
| 后交互 | 交互块最长、最易出错，放最后不影响其他组件 |
| planning 最先剥离 | `<konatan_planning~>` 属于思考过程，用户永远看不到 |

多个同类标签同时出现时：**时间取第一组，音乐/图片/交互各取第一个，其余丢弃并记日志。**

## 8. 真实失败模式

| 失败 | 现象 | 处理 |
|---|---|---|
| 漏闭合 | `<music_recommend>` 没有结束标签 | 解析到下一个标签或消息尾即视为闭合 |
| 标签套正文 | 模型把整段正文包进 `<interact>` | 长度阈值保护：超过 200 字不视为交互 |
| 伪标签 | 模型输出"（此处播放音乐）"而不写标签 | 无法解析，按纯文本处理；通过预设中的正例纠正 |
| 表演遵守 | 表面不写禁词，换成另一种套话 | 定期重读产出、淘汰失效规则 |
| 模型换代 | 新模型对格式的遵循度骤降 | 协议不变、只调预设；这是"协议与提示词分离"的收益 |

---

## 9. 版本与兼容

- 当前为 **v0.1**，未标准化，换前端需重新实现解析器。
- 下一个目标：把本文档抽象成 **JSON Schema**，让解析器可以自动生成，从而迁移到 ST 之外的前端。
- 兼容原则：**只增不改**——新增标签不破坏旧解析器；字段语义变更必须升版本号。
